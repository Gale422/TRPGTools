## TODO管理方針

**基本原則**: 未実装TODOセクションには今後実装すべき内容のみを掲載し、完了した項目を完了マークやチェックボックスで残さない。実装済みの内容は必ず未実装TODOから削除し、実装済み仕様セクションへ移して正式な仕様として記載する。

**補足ルール**:

- TODOを追加する際は、実装に必要な背景と完了条件を簡潔に記載する。
- 実装が完了したら、同一コミット／PR内で仕様セクションを更新し、関連リンクや目次も同時に整える。
- 実装順序やフェーズのような固定スケジュールは維持せず、作業時に都度決定する（優先順位は後述の基準を参照）。
- リファクタリングや軽微な整理は必要に応じて常時行い、仕様変更を伴う場合のみTODOとして記録する。
- TODO項目には「完了」「済」などの状態を記載しない。未実装タスクのみを残す。

**実装完了時の手順**:

1. 実装が完了した機能を確認し、期待する動作条件を満たしているかを確認する。
2. 未実装TODOセクションから該当項目を削除する。
3. 実装済み仕様セクションの適切な場所に仕様として文章を追記・更新する（必要に応じて新しい小見出しを作成）。
4. 関連するリストや参照（他のTODOからのリンクなど）があれば更新または削除する。
5. 目次および内部リンクを必要に応じて更新する。

**注意**: 上記方針は今後追加されるTODOにも必ず適用し、仕様との差分を発生させない。

## 優先順位の判断基準

作業の優先度は、各タスクに着手する直前に以下の観点を重み付けして決定する。固定の実装順序は設けず、状況に応じて見直す。

1. **ユーザー影響度**
   - クリティカル: ツール全体が利用不能／セッション中断レベル。即対応。
   - メジャー: 主要フローを妨げるが回避策がある。回避策の負荷と利用頻度を勘案して順次対応。
   - マイナー: UX低下や限定的な不具合。後回しにできる。

2. **再現性と適用範囲**
   - すべての利用環境で再現するか、特定OS/ブラウザに限定されるかを明確化し、全体影響が大きいものを優先。

3. **回避策・緩和策の有無**
   - 運用で一時的にしのげる場合は優先度を1段階下げ、緩和策がないものを上げる。
   - 例: Windows ZIPブロック問題はXMLダウンロード＋`Unblock-File`で回避可能なため、クリティカル扱いからメジャー扱いへ引き下げた。

4. **依存関係・土台整備**
   - 他タスクの前提になる仕様調整・データ構造変更は早めに実施し、同一領域を連続して触ることで二度手間を防ぐ。

5. **開発コストとリスク**
   - 小さい改善でも高頻度で使われる場合は早めに拾い、逆に大規模変更は影響調査やテスト体制を整えてから着手する。

6. **保守性・将来の負債**
   - 放置すると仕様乖離やデータ移行コストが膨らむものは優先度を引き上げる。逆に長期的なアイデアは「背景」「想定効果」を追記しておき、機会が来たら掘り起こす。

**手順**:

- 各TODOの冒頭または補足に「影響度 / 回避策 / 依存 / 推奨優先度」を簡潔に記載する。
- 新規TODO追加時は、上記観点をひと通りチェックし、状況が変わった場合は既存TODOの優先度コメントも更新する。
- PRや作業ブランチでは、着手理由と選定基準を明記してレビュアーと認識合わせを行う。

## WindowsセキュリティによるZIPファイルのブロック問題

**課題**:

- ダウンロードしたZIPを展開するとWindowsセキュリティが危険判定を行い、XMLが開けずにツール利用が詰まる。

**変更案**:

1. 生成XML内の危険とみなされる文言・属性を洗い出してリスト化する。
2. XMLGeneratorでサニタイズ処理と警告表示を実装し、危険要素を削除またはユーザーに通知する。
3. ZIP以外の配布経路（例: XML単体ダウンロードボタン）を提供し、ユーザーがMOTWを回避できる手段を案内する。
4. サニタイズ後のZIPを複数のWindows環境で検証し、ブロックされないことを確認する。

**補足**:

- 暫定策としてエネミー編集画面に「XMLダウンロード」ボタンを追加済み。ZIP問題が残るため、正式なサニタイズ手順と検証結果の共有が完了するまでこのTODOは維持する。
- ブラウザ経由で取得したファイルには必ずMark of the Web（Zone.Identifier:3）が付与される。ZIP解凍時に属性が伝播するため、ZIP内容そのものより「取得経路」がブロック原因となる。
- 「プロパティや個人情報を削除」機能でコピーしたZIPはADSが除去されており、その派生ファイルではブロックが再現しない。PowerShellの`Unblock-File`や`Remove-Item -Stream Zone.Identifier`でも同等の結果を得られる。

**原因と調査メモ (2025-11-08時点)**:

- Edge/ChromeでダウンロードしたZIPは自動で`Zone.Identifier`ストリームを保持し、ユーザーが展開するとXMLにも同じゾーン情報が付与される。
- 一括エクスポートは二重ZIP構造のため、外側ZIPのブロック解除だけでは内側ZIPへ解除が伝わらない。内側ZIPに対しても個別解除または再ダウンロードが必要。
- XML内容（タグ名やテキスト）はDefenderの検査対象外で、危険判定はMOTWとSmartScreenポリシーによるもの。サニタイズよりも「安全な生成元」と認識させる仕組みが課題。

**追加の対策案**:

- README/アプリ内で「ZIPを展開する前にブロック解除」「PowerShellで`Unblock-File -Path <解凍先>\\*.xml -Recurse`」「必要であればXMLを直接ダウンロードしてローカルでZIP化」などの運用手順を明示する。
- 一括エクスポート時に内側ZIPを生成せず、ユーザーがまとめてZIP化できるようなオプション（例: フォルダー+XML出力）を検討する。
- 将来的に署名付きZIPや信頼済み発行元としての配布（コードサイニング証明書）を導入できないか調査する。

**影響範囲**:

- [ZIPダウンロード機能](SPEC/08-xml-generation.md#zipダウンロード機能)が生成する全ファイル
- ユドナリウム取込を前提としたXML出力

**実装時の注意**:

- Windows Defenderが危険判定する条件を事前に調査し、検出・サニタイズロジックを具体化する。
- XML内容を変更してもユドナリウムでの動作が保たれるか必ず確認する。
- ログやUIでサニタイズ結果をユーザーに伝え、必要なら手動修正手順を提示する。

## モブエネミーの固定値自動算出の改善

**課題**:

- モブエネミーはアクション/リアクションのみを用いるため能力値が存在せず、固定値自動算出がエラーになる。
- 判定タイプから能力値を参照する現在のUIでは、モブ専用挙動を設定できない。

**変更案**:

1. モブエネミー選択時は「固定値を自動算出」で `{アクション}` / `{リアクション}` / 自由入力のいずれかを選択できるようにする。
2. 選択UIはラジオボタンまたはドロップダウンで提供し、通常エネミー時は従来の判定タイプ方式を維持する。
3. 自由入力を選んだ場合は、現在の手動入力欄をそのまま利用できるようにする。

**影響範囲**:

- [モブエネミーの能力値](SPEC/04-abilities.md#モブエネミーの能力値)
- [判定用コマンドとダメージコマンド](SPEC/07-skills-powers.md#判定用コマンドとダメージコマンド)の固定値自動算出処理
- スキル編集UIの「固定値を自動算出」設定

**実装時の注意**:

- モブ判定フラグでUIを出し分け、通常エネミーの挙動を変更しない。
- `{アクション}` をデフォルトにしつつ、データ構造は既存項目を流用して最小限の更新に抑える。
- 既存スキルデータを壊さないように、新しい選択肢は空値時に従来の挙動へフォールバックさせる。

## ドラッグ・アンド・ドロップによるスキルの並び替え

**課題**:

- スキル順序を「↑」「↓」ボタンでしか変更できず、大量スキルを持つエネミーでは操作が煩雑。

**変更案**:

1. エネミー編集画面のスキル/パワー一覧にドラッグ・アンド・ドロップによる並び替えを導入する。
2. 既存の上下ボタンは残し、ユーザーが任意の方法を選べるようにする。
3. ドラッグ中は挿入位置のハイライトなど視覚的なフィードバックを表示する。

**影響範囲**:

- スキル一覧UI（PC/モバイル双方）
- 並び順を保存するロジック（ローカルストレージ）

**実装時の注意**:

- HTML5 Drag and Drop APIまたはタッチ対応のライブラリを選定し、モバイル操作も考慮する。
- D&D中のスタイルが他コンポーネントと干渉しないようにCSSを分離する。
- 並び順の変更をUndoできないため、意図しない移動が起きた際のケア（例えば確定タイミング）を検討する。

## エネミー一覧のソート順のカスタマイズ

**課題**:

- エネミー一覧は常にレベル順→名前順で固定されており、ユーザーが任意の順序で管理できない。

**変更案**:

1. エネミーカードをドラッグ・アンド・ドロップで並び替えられるようにし、カスタム順序をローカルストレージへ保存する。
2. カスタム順が設定されている場合は新規エネミーを末尾に追加する。
3. 「デフォルトのソート順に戻す」ボタンを設け、レベル→名前の自動ソートに戻せるようにする。

**影響範囲**:

- エネミー管理画面
- DataManager等の並び順保存処理

**実装時の注意**:

- ドラッグ操作は前タスク（スキル並び替え）と同じ実装方針を流用し、UIの一貫性を保つ。
- カスタム順とデフォルト順の切り替え条件を明確にし、状態をユーザーに表示する。
- 新規エネミー追加時にどちらのソートモードなのかを判定し、挙動がぶれないようにする。

## 汎用的なスキルの一括取り込み機能

**課題**:

- 既存のテキスト形式スキルリスト（例: `_/_/_/_/_/武器_/_/_/` で区切られたデータ）を一括でライブラリに登録できず、手動で1件ずつ入力している。

**変更案**:

1. スキル・パワーライブラリに「一括インポート」ボタンを追加し、テキストエリア貼り付けまたはファイル読み込みで複数スキルを投入できるようにする。
2. 既存のスキル書式をパースしてライブラリへ追加し、そのまま編集・修正できるUIを提供する。
3. 取り込んだスキルはローカルストレージへ保存し、通常のライブラリ選択フローからエネミーに追加できるようにする。

**影響範囲**:

- [スキル・パワーライブラリ](SPEC/07-skills-powers.md#スキルパワーライブラリ)
- [ライブラリからのスキル選択](SPEC/07-skills-powers.md#ライブラリからのスキル選択)

**実装時の注意**:

- パース失敗時には具体的なエラー箇所をユーザーに伝える。
- 大量データの取り込みでUIが固まらないように逐次処理や進捗表示を検討する。
- 既存データとの重複登録や差分更新方法も合わせて設計する。

## スキル一覧のチャットパレット順ソートボタン

**課題**:

- エネミー編集画面のスキル一覧は登録順で固定されており、チャットパレット生成時の並び（自動的に種別や行動順で整列）と乖離する。戦闘中に参照する順番を統一できず、手動で並び替える手間が発生している。

**期待する動作**:

- スキル一覧の上部に「チャットパレット順で並び替え」ボタンを追加し、押下時に現在のエネミースキルをチャットパレット生成と同じソートルールで即時並び替える。
- 並び替え後は登録順を更新し、ユーザー操作（ドラッグ＆ドロップや再度のソート）でのみ順序を変更できる。元の順番へ自動で戻す機能は不要。
- 保存・エクスポート・XML生成はチャットパレットのタイミングごとのグルーピングを維持したまま、そのグループ内の並びをエネミー編集画面の上→下に一致させる。タイミング境界を崩さずに順番だけを合わせる。

**実装案**:

1. チャットパレット出力ロジックで使用しているソートキー（カテゴリ→行動タイミング→パワー種別など）を共通ユーティリティ化し、スキル一覧でも再利用できるようにする。
2. ソートボタン押下時は整列後の配列を新たな保存順としてローカルストレージ等へ永続化することで、保存時やXML出力時も同じ順番を保つ。
3. XML生成ロジックを更新し、タイミングごとのグループを維持したソート結果を受け取り、各グループ内の順序をUIの表示順へ合わせる。

**影響度・優先度メモ**:

- 主要UI操作の効率化に直結し、チャットパレット活用時の取り違え防止につながる。クリティカルではないが、既存データが多いユーザーほど負担が大きいため中～高優先度で扱う。

## スキル・パワーの分類・タグ機能

**課題**:

- ライブラリ内のスキル数が増えると検索や分類が困難になり、目的のスキルへ素早くアクセスできない。

**変更案**:

1. スキルにカテゴリ（基本カテゴリ＋ユーザー定義）を付与し、カテゴリでのフィルタリング・検索を可能にする。
2. 複数タグを自由入力で設定できるようにし、タグでもフィルタリング可能にする。
3. カテゴリ管理画面を用意し、ユーザー定義カテゴリの追加・削除や使用状況の警告を行う。
4. 基本カテゴリ（武器/魔法/特殊/拡張/強化/支援・妨害/種族/フェイス/パワー/その他）は削除不可として扱う。

**影響範囲**:

- [スキル・パワーライブラリ](SPEC/07-skills-powers.md#スキルパワーライブラリ)
- ライブラリ検索UI、スキルデータ構造、ローカルストレージ

**実装時の注意**:

- 既存スキルに対するカテゴリ/タグ付けの初期値とマイグレーションを設計する。
- カテゴリ削除時に当該カテゴリを使用しているスキルがある場合は警告を表示し、置き換え手段を提供する。
- 基本カテゴリ一覧を定数化し、ほかのツールへ展開しやすい構造にする。

## XMLプレビューの色カスタマイズ機能

**課題**:

- XMLプレビューのシンタックスハイライト色が固定で、ユーザーの視認性や好みに合わせた調整ができない。

**変更案**:

1. XMLプレビュー内に「色設定」UIを追加し、タグ名/属性名/属性値/テキスト/宣言/コメント/CDATAごとの色を変更できるようにする。
2. カラーピッカーまたはカラーコード入力で色を指定し、ローカルストレージに保存する。
3. 「デフォルトに戻す」操作で初期配色へリセットできるようにする。

**影響範囲**:

- [プレビュー機能](SPEC/09-ui-features.md#プレビュー機能)
- プレビュー用CSSおよび設定保存ロジック

**実装時の注意**:

- 色設定の保存キーや構造を明確にし、将来のテーマ機能へ拡張しやすくする。
- 動的にスタイルを適用する際に、既存のclass名（`xml-tag` など）を流用してパフォーマンスを確保する。
- UIが煩雑にならないよう、設定モーダルや折りたたみUIを検討する。

## alert関数ベースの通知廃止

**課題**:

- `alert()` によるモーダルダイアログがUI全体のトーン&マナーから外れており、他の通知方法（トースト/バナー/インラインメッセージ）と一貫性がない。
- ブラウザ標準アラートはユーザー操作を強制的にブロックするため、連続したフォーム入力やデータ編集フローを中断させてしまう。

**変更案**:

1. リポジトリ内のすべてのJavaScriptで `alert()` を検索し、既存のUIパターン（例: 画面下部のトーストやフォーム直下のエラーメッセージ）へ置き換える。
2. 置き換え用の共通通知ヘルパー（例: `showToast(message, type)`）を `script.js` 内に実装し、通知種別（成功/警告/エラー）ごとにスタイルを切り替える。
3. 既存UIと揃えたトランジションや色設定を `style.css` へ追加し、通知表示/非表示のアニメーションを統一する。
4. README/SPECで「alertを使用しない」方針を明文化し、今後の開発時に同様の通知ルールを参照できるようにする。

**影響範囲**:

- `script.js` 全体の通知処理
- エラーハンドリングやフォームバリデーションの表示ロジック
- `style.css` の通知コンポーネント
- 利用者向けドキュメント（通知仕様の説明追記）

**実装時の注意**:

- `alert()` を置き換える際、同期的なユーザー確認（OK/キャンセル）に依存している箇所はUIフローそのものを見直し、非同期でも破綻しない導線へ改修する。
- 通知コンポーネントはスクリーンリーダー対応（`role="status"` 等）を行い、アクセシビリティを確保する。
- 重要エラーと軽微なお知らせで階層を分け、過剰な通知でUXを悪化させないよう優先度判定を導入する。
